# Правила проекта

## Общий порядок работы

- Перед изменением кода изучи текущую структуру проекта и существующую реализацию.
- Сохраняй текущее поведение, если задача явно не требует его изменить.
- Предпочитай небольшие точечные изменения переписыванию файлов целиком.
- Не добавляй библиотеки, фреймворки, сборщики, зависимости или новые файлы без необходимости и явного согласования.
- Задавай уточняющий вопрос только тогда, когда без ответа невозможно продолжить. В остальных случаях принимай разумное решение самостоятельно.
- После изменений кратко сообщай, что было сделано и остались ли нерешённые проблемы.
  
## Качество кода

- Используй семантический и доступный HTML.
- Используй современный TypeScript, React и CSS.
- По умолчанию используй `const`, а `let` — только если значение переназначается.
- Не используй `var`.
- Используй обработчики событий через React props, например onClick; не вставляй JavaScript-код в HTML-строки.
- Не используй устаревшие HTML-атрибуты и устаревшие API.
- Не дублируй логику и разметку.
- Выноси повторяющиеся компоненты и данные в переиспользуемые модули.
- Используй понятные и единообразные имена.
- Не оставляй неиспользуемые параметры, переменные, импорты и мёртвый код.

## Адаптивность

- Сайт должен корректно работать на компьютере, планшете и телефоне.
- Проверяй как минимум ширины:
  - 320 px
  - 390 px
  - 768 px
  - 1024 px
  - 1440 px
- Не допускай горизонтальную прокрутку всей страницы.
- Горизонтальная прокрутка разрешена только внутри предназначенных для неё компонентов, например рядов карточек.
- Изменение внешнего вида фиксированной шапки не должно сдвигать контент.
- Используй адаптивные размеры, отступы и типографику, а не только уменьшенную копию десктопной версии.
- Для полноэкранных мобильных блоков при необходимости используй `svh` или другой подходящий viewport unit.
- Проверяй, что кнопки на мобильном остаются читаемыми и удобными для нажатия.
- Проверяй корректное отображение изображений и видео на всех экранах.
- Мобильное меню не должно сдвигать или ломать контент.

## Доступность

- Все интерактивные элементы должны быть доступны с клавиатуры.
- Для действий используй настоящие `<button>`, а `<a>` — только для реальных переходов.
- Добавляй понятные `aria-label`, если назначение элемента неясно из видимого текста.
- Для нестандартных элементов с ролью кнопки поддерживай `Enter` и `Space`.
- Обеспечивай видимый focus state для всех интерактивных элементов.
- У изображений должен быть подходящий `alt`. Для декоративных изображений используй `alt=""`.
- Обеспечивай достаточный контраст текста и фона.
- Не привязывай важные функции только к hover: они должны работать и на сенсорных устройствах.
- Соблюдай корректную иерархию заголовков (h1 → h2 → h3).
- Используй корректные aria-атрибуты для мобильного меню (`aria-expanded`, `aria-controls`).
- Учитывай `prefers-reduced-motion`: анимации должны отключаться или быть сокращёнными.

### Модальные окна (если добавлены отдельной задачей)

- При реализации модальных окон они должны закрываться по `Escape`.
- Фокус должен быть заперт внутри открытого модального окна.
- При закрытии фокус должен возвращаться на элемент, вызвавший модальное окно.

## Медиаматериалы

### Фотографии и рисунки

- Основные материалы: локальные семейные фотографии и детские рисунки.
- Не используй внешние изображения без необходимости.
- Предпочтительный формат для сайта — WebP.
- Для изображений ниже первого экрана используй `loading="lazy"`.
- Не используй ленивую загрузку для главного hero-изображения.
- Сохраняй пропорции через `object-fit`.
- Предусматривай fallback, если изображение не загрузилось.
- Не показывай fallback-эмодзи или иконку поверх успешно загруженного изображения.
- Показывай атрибуцию, если этого требует источник изображений.
- Не добавляй в Git необработанные фотографии большого размера без необходимости.
- Не заменяй уже выбранные изображения без прямого требования задачи.

### Видео

- Не используй `autoplay`.
- Используй `controls`.
- Используй обложку `poster`.
- Используй `preload="metadata"` или `preload="none"`.
- При отсутствии файла показывай корректную заглушку.
- Не добавляй в Git крупные тестовые видео.
- Длинные и многочисленные ролики в будущем можно вынести на внешний видеохостинг.

## Данные и архитектура

- Повторяющийся контент храни в структурированных данных, а не прописывай каждую карточку или страницу вручную в JSX.
- Тексты историй, подписи, статистика и пути к медиаматериалам не должны храниться непосредственно в компонентах.
- Одна переиспользуемая реализация должна использоваться для однотипных карточек и страниц историй.
- Новая история должна добавляться преимущественно через файл данных, а не через копирование отдельной страницы.
- У каждого элемента должен быть стабильный уникальный `id`.
- Не используй позицию элемента в массиве как постоянный идентификатор.
- Состояние React-интерфейса должно корректно сохраняться при повторном рендере.
- Архитектура должна позволять позднее добавить локализацию, но сейчас не требовать её реализации.

## Внешние API и секреты

- Никогда не записывай ключи, токены, пароли и другие секреты в:
  - HTML;
  - JavaScript / TypeScript;
  - CSS;
  - `CLAUDE.md`;
  - `README`;
  - скрипты, попадающие в Git;
  - вывод команд;
  - скриншоты;
  - логи.
- Получай секреты из переменных окружения.
- Не выводи секрет полностью или частично.
- Не передавай секрет в аргументе команды, если инструмент умеет читать его из переменной окружения.
- Опубликованный статический сайт не должен требовать приватный API-ключ в браузере.
- Используй API во время разработки для получения публичных данных или URL, а в итоговом сайте сохраняй только безопасные публичные значения.
- Перед коммитом проверяй, что секреты отсутствуют в отслеживаемых файлах.

## Git и служебные файлы

- Не добавляй в Git файлы IDE, локальные настройки, секреты, кеши и временные файлы.
- Поддерживай корректный `.gitignore`.
- Не изменяй `.git`, историю, ветки и remotes без прямого запроса.
- Не выполняй commit и push без прямого запроса.
- Перед коммитом проверяй результат в браузере.
- Используй короткие commit message, описывающие наблюдаемое изменение.

## Требования конкретного проекта

- **Название:** «Задворка 2026»
- **Формат:** статическое React-приложение с отдельными маршрутами
- **Технологии:** React, TypeScript, Vite, React Router
- **Маршрутизация:** HashRouter для совместимости с GitHub Pages
- **Бэкенд:** отсутствует
- **База данных и серверное хранилище:** отсутствуют.
- **Контент хранится в локальных структурированных файлах проекта и публикуется вместе со статической сборкой на GitHub Pages.**
- **Размещение:** GitHub Pages
- **Основной язык первой версии:** русский
- **Английская локализация:** может быть добавлена позднее отдельной задачей
- **Адаптивность:** компьютер, планшет, телефон
- **Структура:** стандартная структура Vite + React (не фиксировать `index.html` как главную точку редактирования)
- **Разделение:** страницы, компоненты, типы и данные должны находиться в отдельных модулях

## Проверка результата

После каждого значимого изменения проверяй относящиеся к задаче пункты:

- приложение запускается без ошибок;
- production-сборка проходит;
- lint проходит, если настроен;
- тесты проходят, если настроены и относятся к изменению;
- маршруты открывают правильные страницы;
- прямое обновление маршрута (F5) не ломает приложение;
- навигация и мобильное меню работают;
- страницы корректно отображаются на основных ширинах (320, 390, 768, 1024, 1440 px);
- нет горизонтальной прокрутки всей страницы;
- фото и видео не выходят за контейнер;
- интерактивные элементы доступны с клавиатуры, а focus state остаётся видимым;
- отсутствующие изображения или видео обрабатываются корректно (fallback);
- пути к ресурсам работают с настройкой GitHub Pages;
- в файлах проекта нет секретов.

Не требуй проверки функций, которых в проекте ещё нет.

Не сообщай, что проверка выполнена, если команда или ручная проверка фактически не выполнялась. Если что-либо невозможно проверить, укажи это прямо.

## Стиль файла

`CLAUDE.md` должен содержать постоянные правила работы над проектом, а не:

- описание всех страниц сайта;
- полный технический план первой версии;
- тексты будущих историй;
- инструкции пользователю по запуску проекта;
- инструкции по публикации для читателя.

Такая информация должна находиться в задачах или в `README.md`.

Избегай повторов между разделами.
